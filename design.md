# Сервис такси

## Граница системы

Сервис такси позволяет пассажиру заказать поездку, найти водителя и отслеживать поездку до её завершения.

| Участник | Что делает |
|---|---|
| Пассажир | Создаёт заказ, смотрит состояние поездки и историю |
| Водитель | Получает предложения, принимает или отклоняет их, отправляет координаты |
| Служба поддержки | Помогает пассажиру и водителю, используя данные поездки |

Система — монолитное приложение, разделённое на внутренние модули.

| Внутренний модуль | Ответственность |
|---|---|
| Поездки | Создание и управление поездками |
| Тарифы | Чтение, сохранение и расчёт тарифов |
| HTTP | Приём запросов и отправка ответов |
| Доступ к данным | Чтение и запись данных приложения |

| Внешний сервис | Ответственность |
|---|---|
| Карты | Отображение карты, точек посадки и назначения, водителей и поездки |
| Уведомления водителям | Отправка предложений поездок в приложение водителя |
| Биллинг | Обработка платежей |

## Требования

Предположим, что за сутки создаётся **200 000 поездок**, а историю открывают **60 000 раз**. Один день содержит 86 400 секунд. Для оценки пика используем коэффициент **4** для пользовательских запросов и **1,5** для координат водителей.

Цели: чтение истории — **p95 менее 50 мс**; объём поездок — около **73 ГБ в год** при размере записи 1 КБ.

| Операция | Сценарий | Средняя частота | Пиковая частота |
|---|---|---:|---:|
| Создание поездки | Пассажир оформляет заказ | 200 000 / 86 400 = **2,31 запроса/с** | **9,26 запроса/с** |
| Чтение состояния | Пассажир запрашивает состояние раз в 5 секунд, средняя поездка длится 15 минут | 200 000 × (900 / 5) / 86 400 = **416,7 запроса/с** | **1 667 запросов/с** |
| Просмотр истории | Пассажир открывает историю поездок | 60 000 / 86 400 = **0,69 запроса/с** | **2,78 запроса/с** |

Расчёт предполагает равномерное распределение запросов в течение суток. Пиковая частота — оценка с применёнными коэффициентами, а не измеренное значение.

## Операции

| Операция | Сценарий | Пиковая частота |
|---|---|---:|
| Создание поездки | Создать поездку по точкам посадки и назначения | **9,26 запроса/с** |
| Чтение состояния | Получить текущее состояние поездки | **1 667 запросов/с** |
| Просмотр истории | Получить историю поездок пассажира | **2,78 запроса/с** |

## Модель данных

`NN` означает, что поле обязательно; `N` — поле может быть пустым.

| Сущность | Поля |
|---|---|
| Passenger | `id`, `name NN`, `phone NN` |
| Trip | `id`, `driver_id N`, `passenger_id NN`, `status NN`, `price NN`, `start_point NN`, `destination_point NN`, `cancel_reason N` |
| TripEvent | `id`, `trip_id NN`, `event NN` |
| Driver | `id`, `name NN`, `is_available NN` |

У пассажира может быть много поездок. Каждая поездка принадлежит одному пассажиру и может быть связана с одним водителем. У поездки может быть несколько событий.

История запрашивается для конкретного пассажира по `passenger_id`. Результат сортируется по времени создания поездки, чтобы новые поездки можно было показывать первыми. Для постраничной загрузки запроса нужны параметры:

- `passenger_id` — чей список поездок получить;
- `limit` — сколько поездок вернуть;
- `cursor` или `offset` — с какой позиции продолжить;
- `sort` — порядок сортировки по времени.

Дополнительные фильтры, например по водителю, статусу или цене, можно добавить, если они нужны пользовательскому сценарию.

## Итог

| Этап | Результат |
|---|---|
| Требование | История поездок должна загружаться с p95 менее 50 мс при объёме около 2 млн поездок |
| Базовый результат | p95 на 2000000 строках HTTP запрос - 15.13ms |
| Решение | Фильтровать поездки по `passenger_id`, сортировать по времени создания и загружать страницу ограниченного размера |
| Повторный результат | p95 на 2000000 строках HTTP - 2.62 |

Пока нельзя сделать вывод, выдержит ли решение заданный объём: нет результатов измерения. Следующий опыт — создать около 2 млн записей, выполнить запрос истории с нужным индексом и без него, затем сравнить p95.
